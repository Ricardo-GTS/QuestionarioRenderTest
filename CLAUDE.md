## Stack confirmada

| Camada | Escolha |
|---|---|
| Backend + Frontend | Django (monolito), Templates server-side + HTMX para trocas parciais de tela |
| Banco | PostgreSQL + extensao `pgvector` (indice HNSW, distancia de cosseno), via `pgvector.django` |
| Embeddings | Ollama local, modelo `bge-m3` |
| Autenticacao | Sessao do Django (cookie `sessionid`, httpOnly). Login com Google e' opcional/aditivo, ver secao "Login com Google" abaixo |
| Moderacao | Flag automatica apos `REPORT_THRESHOLD` reportes (default 3) — sem remocao automatica |
| Painel de admin | Quem estiver em `ADMIN_EMAILS` (.env) vira admin no login — sem coluna `role`, sem auto-promocao (nao confundir com superuser do Django, ver secao "Django Admin nativo" abaixo) |
| Recuperacao de senha | Codigo de 6 digitos por e-mail ("Esqueci minha senha" no login), mesma infraestrutura da confirmacao de e-mail |

**Historico da decisao de stack** (relevante pra nao repetir a mesma discussao): o projeto comecou com FastAPI+SQLAlchemy+Alembic no backend e Reflex (Python compilando pra SPA React) no frontend — decisao tomada numa entrevista de esclarecimento explicita, resumida em duas razoes: (1) o nucleo tecnico do projeto (embedding assincrono + pgvector) pesava mais que o auth/admin gratis do Django, que o MVP inicial nao teria usado mesmo (moderacao era so automatica, sem painel humano); (2) JWT em header (nao cookie httpOnly) foi escolhido por simplicidade, aceitando risco de XSS por ser sistema educacional sem dados sensiveis, evitando lidar com CORS/SameSite entre Reflex e FastAPI. Essa decisao foi **reaberta deliberadamente** depois que o painel de admin (que usa auth/gestao de usuarios de verdade) passou a existir, e o usuario pediu explicitamente um framework "mais confiavel e mais aceito pelo mercado". A migracao para Django + Templates + HTMX foi planejada (plano completo em `/home/ricardo/.claude/plans/planeje-como-seria-migrar-buzzing-coral.md`), implementada, testada e colocada no lugar do FastAPI+Reflex, que foi removido do repositorio (ainda recuperavel no historico do git, commit `9335ff1` e anteriores, se precisar).

**Decisao de arquitetura Django:** sem Django REST Framework, sem SPA separada (React) — Templates server-side + HTMX pra trocas parciais (evita reload completo em acoes como aprovar/rejeitar reporte, responder o quiz). Sem Alpine.js: o fluxo do quiz (unico ponto que precisaria de estado no cliente) usa **sessao do servidor** (`request.session["quiz_question_ids"]`/`["quiz_answers"]`/`["quiz_position"]`/`["quiz_started_at"]`) — cada resposta e cada "Proxima" e' um `hx-post` que troca so' o card da pergunta, HTMX nao guarda nenhum estado proprio.

## Comandos

```bash
# Subir tudo (Postgres+pgvector, Ollama, Django) via Docker
cp .env.example .env
docker compose up --build
# App: http://localhost:8000

# Local sem Docker
cd questionario_django
python -m venv .venv && .venv/bin/pip install -r requirements.txt
cp .env.example .env               # editar ADMIN_EMAILS/GOOGLE_CLIENT_ID se necessario
.venv/bin/python manage.py migrate   # = migrate_schemas (django-tenants): public + cada semestre
.venv/bin/python manage.py runserver
pytest                             # todos os testes, sem skip automatico (Postgres+pgvector precisa estar acessivel)
pytest apps/questions/tests/test_similarity.py -v -k nome_do_teste   # um teste especifico
```

Variaveis de ambiente completas em `.env.example` — `SIMILARITY_THRESHOLD`, `QUIZ_SIZE` e `REPORT_THRESHOLD` nunca devem ser hardcoded no codigo (valor efetivo mora no `Semester` ativo -- um conjunto por semestre, ver "Semestres" abaixo).

Cada app tem seu proprio `services.py` (logica de decisao pura, sem tocar ORM/request — `filter_by_threshold`, `should_flag`, `score_quiz`, `compute_average_score_percent`, `compute_user_reputation`/`compute_all_users_reputation`, `compute_stats`) e `tests/` (unitarios puros + smoke de paginas). Ao adicionar regra de negocio nova, prefira esse padrao em vez de misturar decisao com a query no ORM.

**Fluxo critico (RF02/RF05 — dedupe semantica):** `questions.views.create_question` chama `services.get_embedding` (Ollama, cliente sincrono `httpx.post`, ver "Ollama sincrono" abaixo) → `services.find_similar_active_questions` busca vizinhos via `CosineDistance("embedding", ...)` do `pgvector.django` (indice HNSW, `vector_cosine_ops`) só em `status=active` → se similaridade `>= SIMILARITY_THRESHOLD` (valor efetivo no `Semester` do request), a mesma pagina e' re-renderizada com a lista de perguntas parecidas em vez de salvar (via HTMX, troca só o `#question-form-wrapper`).

**Semestres (django-tenants) -- um schema do Postgres por semestre:** `SHARED_APPS` (schema `public`: `core`, `accounts`, auth/sessions/admin/cache) vs `TENANT_APPS` (`questions`, `quiz`, `moderation` + `contenttypes`): cada semestre (`core.Semester`, `TenantMixin`, schema `s2026_1`...) tem sua copia das tabelas de questoes, respostas, quiz, comentarios, reportes, topicos e o indice HNSW -- **isolamento fisico**, nenhuma query de um semestre enxerga outro, sem precisar filtrar. `apps.core.middleware.SemesterMiddleware` (depois do `AuthenticationMiddleware`) faz `connection.set_tenant()` em TODA request (a conexao e' reaproveitada entre requests): aluno = semestre ativo (unico, constraint parcial `uq_one_active_semester`); admin (`ADMIN_EMAILS`) = o selecionado no seletor do painel (`session["admin_semester_id"]`, padrao o ativo; selecionar NAO muda o ativo). Sem semestre nenhum: so' rotas de conta/login/`/health`/`/admin/semestres` funcionam (`SEMESTER_FREE_PREFIXES`); o resto mostra "Nenhum semestre aberto" (e context processors nao podem tocar em tabela de semestre -- ver `my_questions_badge`). Conta e' unica (`public`); participar = `core.Enrollment` (conta nova ja' nasce vinculada ao ativo via `accounts.signals`; conta antiga sem vinculo cai em `/semestre/participar` pelo `RequireRegistrationNumberMiddleware`, que agora exige matricula E vinculo; admin nao precisa). `core.Semester` guarda os 3 limiares (`get_effective_settings()` devolve o semestre da conexao). Abrir semestre: `core.semesters.open_new_semester` (pagina `/admin/semestres`, exige "Fiz o backup"; cria schema + migrations, copia configuracoes e, se marcado, a lista de topicos; troca o ativo em `select_for_update`; falhou = schema removido); `reactivate` desfaz. Armadilhas: (1) **excluir usuario** tem que passar por `accounts.services.delete_user_everywhere` (limpa schema por schema -- o `delete()` do Django so' ve o schema atual e o FK de outro semestre faria o DELETE falhar); o `/django-admin/` nao exclui usuario; (2) **migrations** rodam em todos os schemas (`migrate` = `migrate_schemas`); (3) **testes**: `conftest.django_db_setup` cria o semestre de teste `s2026_1` uma vez e `_active_semester_schema` poe todo teste com banco nele; **nao usar `django_db(transaction=True)`** (o flush apagaria o semestre de teste) -- use `django_capture_on_commit_callbacks`; abrir semestre dentro de teste funciona (DDL transacional, rollback no fim); (4) a thread de envio de e-mail abre conexao nova em `public` (hoje so' toca `EmailSendLog`); (5) comandos que mexem em questoes rodam por semestre (`tenant_command ... --schema=`). O nome do semestre aparece em 4 lugares -- `Semester.name`, o schema (`schema_name_for`: "2025.2" -> `s2025_2`, que o `backup_semestre.sh` deriva do nome), o `Domain` e o arquivo da planilha; renomear so' via `core.semesters.rename_semester` (botao Renomear / `manage.py renomear_semestre`), que troca os 4 juntos (`ALTER SCHEMA RENAME` + `.update()` numa transacao, planilha renomeada no `on_commit`; `.update()` e nao `save()` porque o `TenantMixin.save()` tentaria criar o schema). Migracao do layout antigo (tudo em `public`) para o primeiro semestre: `manage.py criar_primeiro_semestre 2026.1 [--dry-run]` -- move as tabelas com `ALTER TABLE SET SCHEMA` (leva indices/HNSW/identity), copia o historico INTEIRO de `django_migrations` (senao `InconsistentMigrationHistory`: questions depende de accounts) e o `django_content_type` sem ids, confere contagens; ensaiado no banco real restaurado (1.116 questoes, 1.163 linhas, 129 alunos vinculados). Backup: `scripts/backup_db.sh` (completo) e `scripts/backup_semestre.sh 2026.1` (so' o schema), via `pg_dump` do container do Postgres 16 (o do Django nao tem cliente compativel; os scripts nao leem o `.env`, que tem valor com espaco).

**Planilha de backup das questoes (`apps/questions/sheets.py`):** uma planilha por semestre em `QUESTION_SHEETS_DIR` (padrao `BASE_DIR/planilhas`; no Docker o volume `./planilhas:/app/planilhas` -- sem ele o arquivo sumiria ao recriar o container; fora do git e da imagem), no formato das respostas do Google Forms original (aba "Form Responses 1", as 8 colunas que `analise/.../import_question_bank` le pelo nome) + "Situacao". **Sempre regenerada inteira a partir do banco** (`write_sheet`), nunca editada linha a linha: nao desalinha e se conserta na proxima mudanca. Gatilhos: signals `post_save`/`post_delete` de `Question` (`questions/signals.py`) + chamada explicita onde ha `.update()` em lote (`moderation.services.rename_topic`/`delete_topic`). `schedule_sheet_update()` agenda em `transaction.on_commit` e roda numa thread (`QUESTION_SHEETS_ASYNC`, desligado no conftest), agrupando mudancas seguidas do mesmo semestre (`_running`/`_dirty`). Gravacao com `fcntl.flock` (entre os workers) + temporario e `os.replace` (queda no meio nao corrompe); le o banco DENTRO da trava. A falha da planilha nunca impede salvar a questao (so' loga). **Semestre certo na conexao:** dentro de `schema_context()` o django-tenants poe um `FakeTenant` (so' o nome do schema) em `connection.tenant` -- use `core.semesters.connection_semester()` (resolve pelo `schema_name`); `get_effective_settings()` e a planilha usam isso (bug real encontrado: antes caiam no semestre ativo). Planilha por periodo (`available_range`/`parse_range`/`build_range_workbook`, view `core:export_range`): soma TODOS os semestres (questoes importadas tem a data original do formulario, anterior a abertura do semestre -- nao filtrar por `opened_at`), datas inteiras no fuso local, gerada em memoria e so' baixada. Comando `gerar_planilha [--semestre]`.

**Quiz de treino (RF03) -- pagina "Treinar" no menu** (o nome "Questionario" ficou so' pro sistema; URL `/quiz` e app `quiz` nao mudaram): responder (`quiz:answer`) NAO avanca -- devolve o card respondido (acertou/errou, resposta correta, citacoes) com os botoes Proxima, Comentarios e Reportar, que so' existem nesse estado; `quiz:next` so' avanca se a pergunta atual ja' tem resposta. Os dois POSTs mandam o `question_id` da pergunta que estava na tela e o servidor ignora se nao bater com a atual (clique duplo no Proxima, aba desatualizada); resposta nao muda depois de gravada. `quiz_position` e' o indice atual (sessoes antigas sem ele: `len(quiz_answers)`, `quiz.services.current_position`); o quiz em andamento e' retomado ao recarregar e vence em 24 h (`quiz_expired`, `?novo=1` reinicia); pergunta apagada no meio e' pulada (sem 500). **Comentarios:** `questions.QuestionComment` (painel HTMX dentro do card, `questions:comments_panel`), visivel so' via `questions.services.can_view_comments` = admin OU autor da questao OU respondeu a questao no quiz atual (`quiz.views.question_answered_in_quiz`) OU ja' tem comentario visivel nela -- depois do quiz o aluno so' volta as questoes em que comentou, pela aba "Minhas interacoes" (`accounts:interactions`, com selo de comentarios novos via `CommentSeen` e a lista "Meus reportes"). Autor apaga o proprio (hard delete); admin oculta (`removed=True`). Alunos reportam comentario (`CommentReport`, um por aluno, nao o proprio); fila em `/admin/comentarios` com decisao unica por comentario (Remover = oculta + aceita os reportes; Manter = rejeita), sem efeito na reputacao. O reporte da questao tambem abre no painel do quiz (`moderation:report_question?painel=1`, exige ter respondido); o modal continua na pagina de resultado. `report_question` agora exige login (antes um POST anonimo dava 500).

**Minhas Questoes (`questions:mine`, `/minhas-questoes`):** o autor acompanha as proprias questoes -- situacao (Ativa / "Em analise" = `reported` / Removida), filtro `?situacao=` + paginacao 20 (`Paginator.get_page`, pagina/filtro invalido nao dao 500), estatistica de acerto (`QuestionAnswer`, gravado em `quiz.views.answer_question` so' na PRIMEIRA resposta da questao naquele quiz; `user` SET_NULL pra excluir conta nao apagar historico; `services.accuracy_label` so' mostra % com 5+ respostas), motivos dos reportes **sem o reporter** (prefetch `only()` sem o campo, teste confere que o nome nao aparece) e o painel de comentarios. `services.own_questions_for` anota tudo com **subqueries** (`_count`), nunca JOIN (comentarios x reportes x respostas multiplicaria linhas) -- teste `django_assert_max_num_queries` garante que o numero de queries nao cresce com o numero de questoes. Selo do menu "Minhas Questoes (N)": context processor `questions.context_processors.my_questions_badge` (comentarios de outros depois do `CommentSeen`, uma agregacao; 0 em request HTMX/anonimo). Comentarios do autor ganham o chip "Autor da questao"; questao removida = comentarios so' leitura (`services.comments_open`, POST recusado no servidor; apagar o proprio e reportar continuam). Minhas interacoes exclui as questoes do proprio usuario (ficam so' em Minhas Questoes). Testes de rate limit congelam o relogio do django-ratelimit (fixture `ratelimit_on`), e o `DatabaseCache` tem `MAX_ENTRIES=100_000`: o padrao (300) fazia o cull apagar 1/3 das chaves em ordem de `cache_key`, zerando contadores de rate limit ao acaso -- bug real de producao (uma turma gera centenas de chaves) que aparecia como teste instavel; regressao em `test_counter_survives_many_cache_keys`.

**Estatisticas do aluno (`accounts:stats`, `apps/accounts/stats.py`):** `build_user_stats(user)` monta 4 secoes -- Resumo (respondidas, acerto + media da turma, questionarios concluidos, sequencia de dias e recorde, questoes criadas), Meu desempenho (grafico semanal de 8 semanas em SVG gerado no servidor via `weekly_chart`, melhores/piores topicos, cobertura, ultimos questionarios), Minhas questoes como autor (acerto dos OUTROS nas questoes dele, mais respondida/dificil/facil) e Participacao (comentarios, reportes e precisao = aceitos/(aceitos+rejeitados)). Base: `QuestionAnswer` (so' existe desde 24/09/2026 -- a pagina diz "a partir de") e `QuizAttempt` (so' questionarios CONCLUIDOS, gravado no resultado). Minimos: porcentagem por topico/questao so' com 5+ respostas; media da turma so' com 20+ respostas no sistema (anonimato, nunca ranking -- gamificacao esta fora do escopo). Tudo agregado (`values().annotate()`), numero de queries fixo (teste `django_assert_max_num_queries`). Cor do grafico `--color-chart` (#B07818, passo escuro do accent: o #C88A1E dava 2.95:1 contra o card branco; validado com o `validate_palette.js` do skill dataviz). "Treinar este topico": `/quiz?novo=1&topico=<nome>`. **Escolher topicos** (varios): o Treinar continua comecando direto com todos os topicos; o botao "Escolher topicos" no card abre `quiz:choose_topics` (HTMX, dentro do card) com os topicos que tem questao disponivel pro aluno e a contagem (`quiz.services.available_topic_counts`); `pick_random_questions(topics=[...])`; sessao `quiz_topics` (lista) -- `quiz_topic` (texto) e' o formato antigo, lido por `quiz.views._session_topics`; `?topico=A&topico=B` no "Recomecar" (`clean_topics` valida contra `list_topic_names`); nada valido marcado = mensagem e o treino atual continua. **Fuso:** `TIME_ZONE = "America/Recife"` (antes UTC: horarios dos comentarios apareciam 3 h adiantados e dia/semana das estatisticas contariam errado); banco continua em UTC; `tzdata` no requirements pra imagem slim nao depender do zoneinfo do sistema.

**Moderacao (RF04):** `moderation.views.report_question` grava o `Report` (um por par question+reporter — `UniqueConstraint`, view checa antes de criar) e `services.register_report` verifica a contagem; ao atingir `REPORT_THRESHOLD`, muda `Question.status` para `reported` — isso so' controla se a pergunta sai do pool do quiz (`quiz.services.pick_random_questions` so' seleciona `status=active`), **nao** controla o que o admin ve na fila de moderacao (ver abaixo).

`ReportForm` (`apps/moderation/forms.py`) tem so' o campo `reason` (texto livre, **sempre obrigatorio**, 3 a 1000 caracteres) -- nao ha mais lista de tipos de problema. O mesmo vale pro reporte de comentario (`questions.forms.CommentReportForm`, 3 a 500). A coluna `reason_category` foi removida dos dois models (nao havia nenhum reporte no banco quando isso mudou); `reason` e' NOT NULL, e as migrations `moderation/0002_fill_report_reason` e `questions/0008_fill_comment_report_reason` preenchem motivo vazio antigo antes do `AlterField` (migrations separadas, mesma regra do "pending trigger events").

A fila de moderacao (`moderation.views.pending_reports`, `services.list_questions_with_pending_reports`) lista perguntas com **pelo menos 1 `Report.status=pending`**, independente do status da pergunta — de proposito, diferente de `status=reported`, pra um reporte nunca ficar "preso" inacessivel so' porque a pergunta ja saiu desse status (ex: foi removida antes do reporte ser resolvido). Tambem mostra reportes desde o primeiro, antes do auto-flag por `REPORT_THRESHOLD`.

O admin resolve uma pergunta reportada com UMA decisao que cobre a pergunta e TODOS os reportes pendentes dela de uma vez (`services.resolve_reported_question`, views `approve_removal`/`reject_removal`, botoes com `hx-post` que trocam so' o card da pergunta na fila) — nao ha decisao por reporte individual:
- **Aprovar Remocao:** `Question.status = removed` + todo `Report.status=pending` daquela pergunta vira `accepted` (credita quem reportou).
- **Rejeitar Remocao:** `Question.status = active` + os mesmos reportes viram `rejected`.

A tela de moderacao mostra quem criou a pergunta e quem reportou (nome + motivo), mas nao tem edicao inline — editar so' existe na aba "Perguntas Removidas" (`services.update_question`, recalcula embedding se o enunciado mudar, edicao inline via `hx-get`/`hx-post` trocando o card por um form e vice-versa). Uma pergunta ja removida pode ser reativada e editada la (`services.approve_question` — reativa sem mexer em reportes, que ja foram resolvidos quando a pergunta foi removida). Reportes aceitos/rejeitados e perguntas removidas alimentam a reputacao de quem reportou/criou, calculada na hora (`services.compute_user_reputation`), exposta em `accounts.views.my_stats` (pagina "Estatisticas" do aluno) e em `accounts.views.admin_user_list` (visao do admin, via `compute_all_users_reputation` pra evitar N+1).

**Admin da aplicacao (painel do professor):** quem esta em `settings.ADMIN_EMAILS` (.env, lista separada por virgula) vira admin — nao ha coluna `role` nem fluxo de auto-promocao, verificado via decorator `apps.core.permissions.admin_required`/`is_admin_email`, exposto em todo template via context processor `apps.core.context_processors.admin_flag` (nunca expõe a lista de e-mails pro template, so' o booleano `is_admin`). `SIMILARITY_THRESHOLD`, `QUIZ_SIZE` e `REPORT_THRESHOLD` no `.env` sao so' o default inicial (seed do `AppSettings`, que so' serve pra semear o primeiro semestre) — o valor efetivo mora no `Semester` (um conjunto por semestre, copiado do anterior ao abrir um novo) e e' editavel via `moderation.views.admin_settings` (edita o semestre que o admin esta vendo); `questions/services.py`, `quiz/services.py` e `moderation/services.py` leem de la (`core.services.get_effective_settings()`), nunca de `settings` estatico direto pra esses 3 campos.

**Django Admin nativo (`/django-admin/`):** registrado so' pra `accounts.User` (gestao de usuarios, `UserAdmin`), `questions.Question` e `moderation.Report` (inspecao ad-hoc pelo professor/dev). **Atencao:** usa a sessao de auth nativa do Django (superuser via `createsuperuser`), uma credencial **separada** de "email em `ADMIN_EMAILS`" (admin da aplicacao) — nao confundir os dois conceitos, sao logins e propositos diferentes. `pgvector.django.VectorField` retorna um array numpy — colocar o campo `embedding` direto em `readonly_fields` quebra com `ValueError: The truth value of an array... is ambiguous` (o `display_for_field` do admin faz `value in field.empty_values`); a solucao usada foi `exclude = ("embedding",)` + um metodo custom (`embedding_preview`) em `readonly_fields` que converte pra string antes (ver `apps/questions/admin.py` e o teste de regressao `apps/questions/tests/test_admin.py`).

**Login com Google (opcional, aditivo):** `accounts.views.google_login` recebe o id_token do Google (`credential`, via form POST do botao Google Identity Services, JS vanilla do proprio Google, sem lib Python de frontend), verifica assinatura/audience/expiracao via `google-auth` (`accounts.services.verify_google_id_token`, audience = `GOOGLE_CLIENT_ID`) e cria a sessao Django com `django.contrib.auth.login()` — nao ha JWT nem estado paralelo. Resolve o usuario por `google_sub` e, se nao achar, por `email` (linka a conta existente em vez de duplicar); so' cria usuario novo se nenhum dos dois bater. Contas so'-Google usam `user.set_unusable_password()` (convencao nativa do Django) em vez de `hashed_password=None` como no SQLAlchemy antigo — o efeito observavel e' o mesmo (`check_password` sempre falha pra essas contas), entao `login()` por email/senha nao precisa de nenhum tratamento especial. Sem `GOOGLE_CLIENT_ID` configurado, o botao nao aparece (`{% if google_client_id %}` no template) — feature desligada, resto do app intacto. **Atencao ao testar:** o Google Identity Services valida a *origin* exata (protocolo+host+porta) contra a lista de "Authorized JavaScript origins" configurada no Google Cloud Console pro Client ID — se a porta/dominio mudar, precisa atualizar essa lista la, senao o botao aparece mas o login falha silenciosamente.

**Matricula da Universidade (`User.registration_number`):** obrigatoria no cadastro, unica, e depois de preenchida so' o admin altera (`accounts.views.admin_update_registration_number`, campo inline no card do usuario em Usuarios, via HTMX) -- em "Conta" aparece so' como leitura; so' digitos (8 a 12, `REGISTRATION_NUMBER_VALIDATOR` em `accounts/models.py`). A coluna e' `null=True` so' por causa de contas criadas pelo login com Google e contas anteriores ao campo: `accounts.middleware.RequireRegistrationNumberMiddleware` redireciona qualquer usuario logado sem matricula para `/conta/matricula` (HTMX recebe `HX-Redirect`) ate ele preencher — liberados so' essa tela, logout, `/health`, `/django-admin/` e estaticos. Em testes, usuario criado via ORM que precisa navegar pela app tem que receber `registration_number`, senao toda request vira 302.

**Confirmacao de e-mail (cadastro e troca de e-mail):** `accounts.views.register` NAO cria o `User` -- grava um `PendingRegistration` (dados + senha ja com hash via `make_password`) e manda um codigo de 6 digitos por e-mail; o `User` so' nasce em `services.complete_registration`, que confere o codigo e checa de novo se e-mail/matricula continuam livres (pendente nao reserva nada). O pendente e' amarrado a **sessao** (`request.session["pending_registration_id"]`), NAO ao e-mail: se fosse um por e-mail, um atacante podia se cadastrar com o e-mail da vitima e sobrescrever a senha do pendente dela antes da vitima digitar o codigo (teste `test_other_session_cannot_overwrite_pending_password`). Codigo: so' o HMAC-SHA256 (com `SECRET_KEY`) vai pro banco, 15 min de validade, 5 tentativas contadas com `select_for_update`; cooldown de 60 s e maximo 5 envios/hora sao **por e-mail de destino** via `EmailSendLog` (nao por pendente/sessao, senao abrir sessoes novas furava o limite). Constantes no topo de `accounts/services.py`. Troca de e-mail na Conta: `EmailChangeRequest`, `user.email` so' muda no `complete_email_change`, e o e-mail antigo recebe aviso (`transaction.on_commit` -- nos testes, usar a fixture `django_capture_on_commit_callbacks`). Login com Google continua criando a conta direto (`verify_google_id_token` ja exige `email_verified`). Envio: `EMAIL_BACKEND` SMTP se `EMAIL_HOST` definido, senao console; Mailpit no docker-compose (dev, http://localhost:8025) e Gmail com senha de app em producao, so' trocando o `.env`. Testes: helper `conftest.register_user(client, data)` faz o fluxo inteiro (le o codigo de `mail.outbox`) -- use ele em vez de `client.post(reverse("accounts:register"), ...)` quando o teste so' precisa de um usuario logado.

**Recuperacao de senha:** `accounts.views.password_reset_request` -> `password_reset_confirm` (codigo + nova senha na mesma tela) -> `services.complete_password_reset`. Reusa a mesma infraestrutura da confirmacao de e-mail (`EmailCodeBase`, `issue_code`/`_check_locked`, `EmailSendLog`, template `confirm_code.html` generico via `views.CONFIRM_PAGES`). `PasswordResetRequest` e' um por usuario (OneToOne). O aluno informa **e-mail ou matricula** (`ForgotPasswordForm.clean_identifier` devolve `("email"|"registration_number", valor)`, guardado na sessao em `password_reset_identifier`); o codigo sempre vai pro e-mail cadastrado na conta, e pela matricula a tela NAO mostra o e-mail mascarado (entregaria que a matricula existe). **Anti-enumeracao:** resposta, tela, timers e mensagem de erro sao identicos com ou sem conta pro e-mail (por isso o erro de codigo da redefinicao nao mostra "restam N tentativas", e `start_password_reset` nao devolve nada) -- o cadastro ainda revela "ja existe conta com esse e-mail", aceito de proposito. Trocar a senha desloga as outras sessoes (hash de sessao do Django) e manda aviso ao e-mail; conta so'-Google tambem pode definir senha por aqui; conta inativa nao recebe codigo.

**Confirmar que e' voce (pagina Conta):** o nome e' editavel direto, mas e-mail e senha ficam travados ate o usuario digitar um codigo enviado ao e-mail ATUAL (`views.reauth_start` -> `confirm_reauth`, `ReauthRequest`, `services.start_reauth`/`complete_reauth`); o codigo certo grava `request.session["reauth_until"]` e libera por `REAUTH_MINUTES` (10). O travamento e' no servidor: sem isso, `AccountForm(reauthenticated=False)` marca os campos como `disabled` (Django ignora o POST e usa o `initial`). Vale igual pra conta com senha e conta so'-Google (por isso codigo, nao "digite a senha atual"). Troca de e-mail continua pedindo o codigo do NOVO e-mail depois; troca de senha desloga as outras sessoes e manda aviso. Nos testes que trocam e-mail/senha, confirmar a identidade antes (ver `_logged_user` em `test_email_verification.py` e `test_reauth.py`).

**Ollama sincrono (nao async):** `questions.services.get_embedding` usa `httpx.post` sincrono (nao `httpx.AsyncClient`) porque as views sao Django comuns (sync), nao ha DRF nem necessidade de ASGI so' por causa dessa chamada — o bloqueio do worker durante a chamada e' aceitavel com multiplos workers (`gunicorn -w N`) e volume baixo de criacao de perguntas (projeto academico). `google.auth.transport.requests` (usado por `verify_google_id_token`) exige o pacote `requests` instalado separadamente — nao vem como dependencia transitiva do `google-auth`, mesmo sendo importado por ele. **Workers e desempenho (medido):** o `Dockerfile` roda `gunicorn --workers ${GUNICORN_WORKERS:-4}` -- com 1 worker (o padrao, que era o que rodava antes), um request esperando o Ollama/SMTP travava todos os outros. O Ollama descarregava o `bge-m3` apos 5 min ocioso e a 1a pergunta seguinte levava ~12 s; agora `OLLAMA_KEEP_ALIVE=-1` no servico `ollama` (docker-compose, ~1,2 GB de RAM fixos) + `manage.py warm_ollama` em background no CMD (carrega o modelo na subida, nunca falha o boot). Com varios workers o cache do `django-ratelimit` precisa ser compartilhado: `DatabaseCache` (tabela `django_cache`, `createcachetable` no CMD; nao-atomico, aceitavel aqui -- Redis se o volume crescer). `django_ratelimit.middleware.RatelimitMiddleware` e' o que transforma o bloqueio em `RATELIMIT_VIEW` (429); sem ele virava 403 generico (bug que existia ate' isso ser adicionado). E-mail: `accounts.services.dispatch_email` envia numa thread em background quando `EMAIL_SEND_ASYNC=true` (default; a tela nao espera os ~2 s do Gmail) -- o `EmailSendLog` e' gravado antes e apagado se o envio falhar (reenvio fica livre); `conftest.py` desliga o async nos testes.

**`pgvector.django`:** `VectorField(dimensions=1024)` + `HnswIndex` em `Meta.indexes` (com `m=16, ef_construction=64, opclasses=["vector_cosine_ops"]`) **e'** reconhecido pelo `makemigrations`, que gera a `AddIndex` sozinho — nao precisa de SQL manual pro indice. A extensao `vector` do Postgres precisa de operacao manual (`pgvector.django.VectorExtension()`) e fica no schema **public**: criada em `core/0002_semesters.py` (app compartilhada) ANTES dos schemas de semestre -- a de `questions/0001` roda dentro de cada schema e, num banco novo, prenderia o tipo `vector` no primeiro schema. Os enums de status (`QuestionStatus`, `ReportStatus`) sao `models.TextChoices` — viram `varchar`+`choices` no banco (validacao so' em nivel de aplicacao), nao um tipo `ENUM` nativo do Postgres.

**Trocar o modelo de embedding (ja aconteceu uma vez: `nomic-embed-text` 768d → `bge-m3` 1024d, 2026-09-20):** motivo — `nomic-embed-text` dava similaridade alta (~0.82) pra perguntas com o mesmo molde gramatical mas fatos diferentes (ex: "a capital do Brasil e Brasilia" vs "a capital da Franca e Paris"), quase colando no valor de parafrases reais (~0.98) e deixando pouca margem pra calibrar o threshold. Testado empiricamente (nao so' por ranking de leaderboard — `multilingual-e5-large-instruct`, #1 em STS-PT no MTEB, na pratica separou pior que `bge-m3` aqui) com 3 pares de frase (parafrase / mesmo-molde-fatos-diferentes / sem-relacao) em 5 modelos via Ollama `/api/embeddings` direto, comparando o "gap" de cosseno entre parafrase e falso-positivo. `bge-m3` venceu (gap 0.31 vs 0.16 do `nomic-embed-text`). Trocar modelo de embedding exige SEMPRE mudar 4 coisas juntas, nunca so' o nome: `EMBEDDING_DIM` em `apps/questions/models.py`, uma migration de `AlterField` na coluna `embedding` (**em migration SEPARADA de qualquer `RunPython` que apague/limpe dados antes** — Postgres nao permite `DELETE` que dispara trigger de FK e `ALTER TABLE` na mesma transacao, erro real: "cannot ALTER TABLE because it has pending trigger events"), o `OLLAMA_EMBED_MODEL` no `.env`, e o `SIMILARITY_THRESHOLD` (a escala de similaridade muda de modelo pra modelo). `apps/questions/management/commands/recompute_embeddings.py` recalcula o embedding de perguntas existentes com o modelo atual (por semestre: `manage.py tenant_command recompute_embeddings --schema=s2026_1`, ou `all_tenants_command recompute_embeddings` pra todos) — rodar depois de qualquer troca de modelo se houver dado real a preservar (da vez que isso aconteceu, so' havia 1 pergunta de teste, entao a migration simplesmente apagou as perguntas em vez de recalcular).

**Numeros e locale:** `LANGUAGE_CODE = "pt-br"` faz o filtro de template `floatformat` exibir numeros com virgula decimal (ex: "0,98" na exibicao informativa de similaridade) — mas os campos de formulario (`FloatField`/`IntegerField` em `AppSettingsForm`) continuam esperando ponto, porque tem `localize=False` por padrao no Django. Isso **nao e' um bug** (confirmado testando o POST em `/admin/configuracoes`), so' uma inconsistencia cosmetica entre texto informativo (locale-aware) e campo editavel (sempre ponto).

**Container sem root:** o `Dockerfile` cria o usuario `app` (UID/GID 1000 por padrao, `--build-arg APP_UID/APP_GID`) e roda com `USER app` -- nada precisa de privilegio (porta 8000; so' le codigo/estaticos, que continuam do root, e grava no volume `planilhas/`). Os arquivos do volume ficam com o dono certo no servidor. O usuario tem `--create-home` porque o gunicorn 26 cria o socket do "control server" no `$HOME` (sem a pasta: "Control server error: Permission denied"). `PYTHONDONTWRITEBYTECODE=1` (o app nao consegue gravar .pyc no codigo). Se a pasta `planilhas/` ja' existir com dono root no servidor (criada antes dessa mudanca), trocar o dono uma vez: `docker run --rm --user root --entrypoint chown -v $PWD/planilhas:/p questionario-django -R 1000:1000 /p`.

**Producao:** estaticos servidos via `whitenoise` (`STORAGES["staticfiles"] = "whitenoise.storage.CompressedManifestStaticFilesStorage"`), sem precisar de nginx separado — `collectstatic` roda no build da imagem Docker (`questionario_django/Dockerfile`). `.env` na raiz do repo e' lido tanto pelo `docker-compose.yml` (interpolacao de variaveis) quanto por `python-dotenv` dentro do container (`config/settings.py::load_dotenv`) — nao precisa exportar nada manualmente.

## Testes

`questionario_django/` (raiz do projeto Django) tem duas categorias, todas via `pytest`+`pytest-django`:
- **Unitarios** (`apps/*/tests/test_*.py` cobrindo `services.py` de cada app): puros, sem `@pytest.mark.django_db`, rodam em qualquer lugar sem banco.
- **Integracao** (`tests/test_integration_flow.py`, `tests/test_pages_render.py`, `apps/questions/tests/test_admin.py`): usam `@pytest.mark.django_db` + `django.test.Client` contra um Postgres+pgvector real — **sem skip automatico** (diferente do `requires_db` que o backend antigo tinha; aqui presume-se que o Postgres de dev/CI esta acessivel). `conftest.py` (raiz) fixa `ADMIN_EMAILS={"admin@example.com"}` e desliga `RATELIMIT_ENABLE` via fixture `autouse`; a fixture `fake_embedding` faz `monkeypatch.setattr("apps.questions.services.get_embedding", ...)` com um embedding deterministico por hash simples do texto, pra nao depender do Ollama real nesses testes (view e `moderation.services.update_question` sempre chamam `services.get_embedding` — nunca importam o nome solto — exatamente pra esse monkeypatch pegar os dois pontos de chamada).

## Especificacao de requisitos (referencia)

Requisitos funcionais e nao funcionais originais do projeto — uteis para checar se uma mudanca ainda atende ao escopo do MVP. Sao independentes da stack de implementacao (foram escritos quando o projeto era FastAPI+Reflex, continuam validos com Django).

### Visao geral do produto

Plataforma web onde alunos se cadastram, criam perguntas de Verdadeiro ou Falso sobre qualquer conteúdo de estudo, e respondem questionários montados aleatoriamente a partir do banco de perguntas de todos os usuários. O sistema evita duplicação semântica de perguntas usando embeddings + busca vetorial.

### Requisitos Funcionais (RF)

**RF01 — Cadastro e autenticação**
- Aluno se cadastra com nome, e-mail, matrícula e senha; a conta só é criada depois de confirmar o e-mail com o código de 6 dígitos enviado para ele.
- Login com e-mail/senha (sessao do Django, cookie httpOnly).
- Login alternativo com Google (opcional/aditivo, adicionado após o MVP) -- cria ou vincula a conta pelo e-mail, sem exigir senha.
- Aluno pode editar seus dados de conta (nome, senha, e-mail); trocar e-mail ou senha exige um código enviado ao e-mail atual. Não pode excluir a própria conta (removido depois do MVP — só o admin exclui usuários, em Usuários) nem alterar a matrícula depois de preenchida.
- Recuperação de senha: "Esqueci minha senha" no login, com código de 6 dígitos enviado ao e-mail da conta (adicionado após o MVP).

**RF02 — Criação de perguntas V/F**
- Usuário autenticado cria uma pergunta: enunciado (texto), resposta correta (Verdadeiro/Falso), categoria/tema opcional.
- Antes de salvar, o sistema calcula o embedding do enunciado e busca no banco vetorial perguntas existentes com **similaridade ≥ 75%** (configurável).
  - Se encontrar, a pergunta é **descartada** (não salva) e o sistema exibe ao usuário a(s) pergunta(s) já existente(s) mais similar(es).
  - Se não encontrar, a pergunta é salva normalmente, com seu embedding persistido junto.
- Cada pergunta guarda: autor, enunciado, resposta correta, embedding, categoria, data de criação, status (ativa/reportada/removida).

**RF03 — Questionário aleatório**
- Usuário solicita um questionário; o sistema seleciona X perguntas aleatórias (configurável, default 10) dentre as perguntas ativas de outros usuários (exclui as do próprio usuário). Opcionalmente, só de um tópico ("Treinar este tópico", na página de Estatísticas).
- Usuário responde V ou F para cada pergunta e vê na hora se acertou e a resposta correta; só avança quando clica em "Próxima" (adicionado após o MVP).
- Depois de responder, pode ler e escrever comentários na questão e reportá-la, sem sair do card; depois do quiz, só volta aos comentários das questões em que comentou (aba "Minhas interações").
- Ao final, sistema mostra pontuação (acertos/total) e feedback por pergunta.

**RF04 — Reporte de perguntas**
- Usuário pode reportar uma pergunta como incorreta/problemática escrevendo o motivo (texto livre, **sempre obrigatório**; a lista fechada de tipos de problema foi removida depois do MVP). Comentários de outros alunos também podem ser reportados, com a mesma regra.
- Um usuário só pode reportar a mesma pergunta uma vez.
- Reportes ficam associados à pergunta e ao usuário que reportou, com data.
- Regra de moderação: flag automática para revisão após N reportes (default configurável 3), sem remoção automática definitiva.
- Cada reporte individual é aceito ou rejeitado pelo admin (ação separada de aprovar/remover a pergunta). Reportes aceitos contam para a reputação de quem reportou; perguntas removidas contam como penalidade para quem as criou -- ambos visíveis para o usuário numa página "Estatísticas" e para o admin em Usuários (adicionado após o MVP).

**RF05 — Detecção de similaridade semântica (núcleo técnico)**
- Embedding do enunciado gerado localmente via Ollama (`bge-m3`).
- Embeddings persistidos no Postgres via `pgvector`.
- Busca de vizinhos mais próximos por similaridade de cosseno, limiar configurável (env var como seed, valor efetivo por semestre, nunca hardcoded — default `0.80`).

### Requisitos Não Funcionais (RNF)

- **Stack:** Django (Templates + HTMX), Postgres+pgvector, Ollama local (sem API paga externa).
- **Persistência:** Django ORM + migrations versionadas.
- **Segurança:** senhas com hash forte (bcrypt via `BCryptSHA256PasswordHasher`), validação de entrada em todos os formulários (Django Forms). Rate limiting via `django-ratelimit`, **por alvo e não por IP** (regras em `apps/core/ratelimits.py`): login/cadastro 5/min por e-mail tentado, recuperação de senha 5/min por e-mail/matrícula, códigos na Conta por usuário, criação de pergunta 20/min por usuário; por IP só um teto alto (300/min somando as telas de conta, 1000/min na criação de pergunta). Motivo: a turma inteira sai pelo mesmo IP (NAT do Wi-Fi da universidade) e um limite baixo por IP bloquearia todo mundo a partir do 6º login. Atrás de proxy, `TRUSTED_PROXY_COUNT` (.env) faz o IP vir do `X-Forwarded-For` (`ratelimits.client_ip`); 0 = acesso direto, e nunca aumentar sem proxy de verdade (o cliente forjaria o header). CSRF via `{% csrf_token %}` + header `X-CSRFToken` nas requisições HTMX.
- **Performance:** índice `hnsw` no pgvector para a busca vetorial; geração de embedding é síncrona (ver "Ollama sincrono" acima).
- **Testes:** unitários para threshold de similaridade, seleção aleatória/scoring; integração para os principais fluxos (ver seção "Testes").
- **Observabilidade:** `/health` verificando Postgres e Ollama.
- **Containerização:** `docker-compose.yml` orquestra Django, Postgres+pgvector e Ollama; variáveis de ambiente via `.env`.
- **Usabilidade:** fluxo de quiz responsivo em mobile; mensagens de erro claras (ex: pergunta duplicada mostra a pergunta similar).

### Semestres (adicionado após o MVP)

- Cada semestre é isolado (schema próprio): questões, questionários, duplicatas, tópicos, estatísticas e configurações próprios. O semestre novo começa do zero; os anteriores ficam guardados, e o admin consulta e modera qualquer um pelo seletor do painel.
- Contas são únicas: o aluno mantém login e senha; no semestre novo, escolhe "Participar".

### Fora de escopo (MVP)

- Gamificação (ranking, pontos, badges).
- Perguntas em formatos além de V/F (múltipla escolha etc.).
- Tabela de auditoria dedicada para ações do admin (hoje é só log estruturado, sem histórico consultável).

### Painel de admin (professor) — adicionado após o MVP

Requisito posterior ao MVP inicial: `role`-free (via `ADMIN_EMAILS`), moderação de perguntas reportadas (aprovar/remover/editar com recálculo de embedding), gestão de usuários (listar + excluir), dashboard (totais, taxa média de acerto via `QuizAttempt`, perguntas por tópico), e os 3 thresholds de negócio editáveis em runtime. Ver seção "Arquitetura" acima para os arquivos.

**Topicos (aba "Topicos", `/admin/topicos`):** `Question.topic` continua texto livre (nao FK). O model `questions.Topic` e' so' um catalogo pra guardar topicos criados pelo admin que ainda nao tem pergunta; a lista exibida nos selects e na aba e' a uniao do catalogo com os topicos ja usados (`questions.services.list_topic_names`). Renomear (`moderation.services.rename_topic`) atualiza todas as perguntas; renomear pra um nome ja existente e' recusado. Excluir (`delete_topic`) um topico em uso tem dois botoes: "Mover Questoes e Excluir Topico" (`reassign_to`, move as perguntas pra outro topico -- e' tambem a forma de juntar dois topicos) ou "Excluir Topico e Questoes" (`delete_questions=True`, hard delete das perguntas, com os reports delas em cascata, o que tambem some da reputacao).

Adicionado depois disso: login opcional com Google (ver seção "Login com Google" acima) e veredito individual por reporte (aceitar/rejeitar, alimentando a reputação do usuário -- ver seção "Moderação (RF04)" acima).
